# Замеры batching bbolt и S3-FIFO

При параллельных установках отдельный fsync на каждую запись ограничивает
скорость метаданных, а удаление файлов под блокировкой задерживает новые
пакеты. Замеры от 2026-10-10 сравнивают прежний код с адаптированным batching
и очисткой из unionai. Это измерение отдельных операций, а не времени pipeline.

## Результаты

Медианы пяти запусков; throughput рассчитан как 1e9 / медиана ns/op.
Задержки — медианы p50/p95 отдельных запусков, не общий квантиль всех запросов.

| Сценарий | До | После | Изменение |
| --- | ---: | ---: | ---: |
| bbolt, 1 писатель | 776 записей/с | 755 записей/с | −2,7%; близко к разбросу запусков |
| bbolt, 4 писателя | 760 записей/с | 2248 записей/с | ×2,96 |
| bbolt, 16 писателей | 805 записей/с | 7603 записей/с | ×9,45 |
| npm-индекс, 4 писателя, включая сжатие | 1036 записей/с | 2222 записей/с | ×2,14 |
| Admit во время удаления файла (p50) | 20,345 мс | 0,033 мс | исчезло ожидание удаления |

| bbolt | p95 до | p95 после | Commit на запись до → после |
| --- | ---: | ---: | ---: |
| 1 писатель | 1,667 мс | 1,674 мс | 1 → 1 |
| 4 писателя | 6,433 мс | 1,967 мс | 1 → 0,2505 |
| 16 писателей | 21,668 мс | 2,694 мс | 1 → 0,06263 |

Вариант с безусловным Batch и задержкой 10 мс из форка проверен отдельно
тремя запусками: 1/4/16 писателей — около 93/367/1412 записей/с. При четырёх
писателях это медленнее исходного Update. Поэтому итоговая версия фиксирует
одиночные записи сразу, а пересекающиеся группирует с задержкой до 1 мс.
Размер группы — до 100 callbacks; fsync остаётся включённым.

## Условия

- Сервер раннера `109.172.97.212`: 6 vCPU Xeon Gold 6240, 15 ГиБ RAM,
  Go 1.26.8, Linux amd64, GOMAXPROCS=4.
- БД каждого запуска создаётся в `/var/tmp` на ext4 `/dev/sda1`, как рабочий
  cache. `/tmp` на сервере — tmpfs и для замеров дисковых транзакций не подходит.
- До: commit `74dcbed` (точный SHA в `baseline-commit.txt`). После: изменения
  рабочей копии поверх него. Источник переноса: unionai main
  `10e3bc06e0656701d7ca936248d83d743d7b3c90`.
- MetadataDisk: 128 заранее созданных ключей, payload 4096 байт, параллельные
  перезаписи PutEnvelope. Измеряется запись с TTL-индексом и durable commit.
- NPMMetadataDisk: 128 ключей, JSON около 32 КиБ; реальный npm Index,
  EnvelopeIndex и zstd. Время HTTP/upstream сюда не входит.
- AdmissionDuringEviction: реальный backend с дополнительной задержкой Delete
  20 мс; измеряется только Admit, пока Delete уже выполняется. Тут специально
  включены NoSync и размер Batch=1, чтобы изолировать блокировки от fsync.
  **Это не ускорение самого удаления файла в сотни раз.**
- Первое обращение к неисправленному benchmark очистки использовало неподдерживаемый
  SHA256 hash. Оно не дало измерений; после замены на BLAKE3 baseline собран
  заново из того же commit и выполнен тем же тестом, что и итоговая версия.
- Исходные benchmark-файлы до/после одинаковы. Сервис и его рабочая БД не менялись.
  Начальная нагрузка была низкой; тесты запускались последовательно. На общей
  виртуальной машине возможен разброс, поэтому приведены пять запусков.

## Повторение

Из каждой версии собрать одинаковые тестовые бинарники:

```sh
CGO_ENABLED=0 go test -c -o metadb.test ./store/metadb
CGO_ENABLED=0 go test -c -o npm.test ./protocol/npm
CGO_ENABLED=0 go test -c -o s3fifo.test ./store/s3fifo
```

Для старого commit benchmark-файлы нужно скопировать из текущей версии;
тесты новых возможностей копировать не требуется.
На сервере выполнить в отдельном временном каталоге на диске:

```sh
export TMPDIR=$(mktemp -d /var/tmp/content-cache-bench.XXXXXXXX)
export GOMAXPROCS=4
./metadb.test -test.run='^$' -test.bench=BenchmarkMetadataDisk -test.benchtime=1s -test.count=5 -test.benchmem
./npm.test -test.run='^$' -test.bench=BenchmarkNPMMetadataDisk -test.benchtime=1s -test.count=5 -test.benchmem
./s3fifo.test -test.run='^$' -test.bench=BenchmarkAdmissionDuringEviction -test.benchtime=100x -test.count=5 -test.benchmem
```

Для подбора параметров MetadataDisk принимает
`CONTENT_CACHE_BENCH_BATCH_DELAY` (например `2ms`) и
`CONTENT_CACHE_BENCH_BATCH_SIZE` (например `16`); NPMMetadataDisk принимает
переменную задержки. После работы удалить созданный временный каталог.

Исходные данные: [before.txt](before.txt), [before-eviction.txt](before-eviction.txt),
[fork-default-10ms.txt](fork-default-10ms.txt), [after-metadata.txt](after-metadata.txt),
[after-npm.txt](after-npm.txt), [after-eviction.txt](after-eviction.txt).
Сводные медианы: [summary.json](summary.json). Окружение: [environment.txt](environment.txt).

## Проверка корректности

`scripts/check.sh` прошёл: форматирование, go vet и полный набор тестов
с race detector. [Вывод](verification.txt). Тест отката неудачного Batch
проверяет атомарность ссылок blob и expiry-индексов; вместе с проверкой
одиночной записи без задержки он дополнительно прошёл 20 повторов под race
detector. Перенесены тесты дубликатов очереди, pinned-сканирования, восстановления
кандидата при ошибке удаления и освобождения блокировок. Добавлены тесты
CLI/environment и операционных метрик. Собраны Linux amd64/arm64, SHA256 проверены.

Рабочий сервис оставлен на версии 1.4.0; временные БД и тестовые бинарники
на сервере после замеров удалены.
